# 扫描与数据库性能短测

日期：2026-10-02。Windows x64，AMD Ryzen 9 9950X3D，.NET SDK 10.0.401 / runtime 10.0.12，Release。数据库位于本地新工作区；Microsoft.Data.Sqlite 10.0.11、SQLitePCLRaw 2.1.12，WAL 与 synchronous=FULL。没有打开旧 ECHO 生产曲库。

## 观测结果

| 场景 | 本轮结果 |
| --- | --- |
| 512 个 WAV 标签夹具首次导入 | 120.95 ms |
| 同目录增量复扫，全部未变化 | 14.75 ms，0 metadata 更新 |
| 增量复扫的全进程托管分配总量 | 609,672 bytes，约 0.58 MiB；不是持有内存 |
| 128 个 WAV 必要 metadata 读取 | 新直接头部路径 11.83 ms，既有 C++ scanner 热进程 stdio 路径 25.15 ms |
| 同 schema/FTS/持久化条件的 512 行写入对照 | 每记录一事务 1119.83 ms；每 128 行批量事务 19.98 ms |
| 50,000 行生成数据批量写入 | 2451.73 ms，含索引、FTS 和批次进度/回执 |
| 大表写入期间抽样分页查询 | 最慢 1.81 ms |
| 200 行分页/搜索混合查询 | 32 个样本的 p95 30.25 ms |
| 按游标完整遍历 50,000 行 | 101.04 ms，无重复/漏行；查询计划使用 tracks_page 索引 |
| 小夹具测试进程 private bytes 采样 | 54.19 MiB |
| 大表测试进程 private bytes 采样 | 89.45 MiB |

直接 WAV metadata 路径在这个热缓存夹具下耗时降低约 53%。这只是同类必要字段的旧组件对照，不代表完整旧 ECHO 已被实测超越。数据库逐条事务是对照模型；旧 Core 已有批次与准备语句优化，不能把这里的约 56 倍比值说成相对旧 Core 的收益。

## 数据与测试范围

512 个 WAV 是短 PCM 加 UTF-8 INFO 标签的人工夹具，FLAC 用 STREAMINFO/Vorbis metadata 夹具验证字段，不包含解码或听感验收。50,000 行是流式生成的真实 SQLite 行，未创建 50,000 首真实音频。大表读写只保留当前批次及当前页，未驻留整库对象。

初轮功能验证通过 16 项，覆盖 import、metadata 字段、排序分页、FTS、增量、旧游标、取消、不完整扫描、missing 清理、回执、写入 owner、持久化、旧库拒绝以及既有 C++ 协议/Unicode 字段对照。后续精度定向验证通过 7 项，覆盖变化中拒绝入库、错误可查询、无效批次原子性、FLAC 字段、未迁移虚拟曲目诊断、增量身份与大小写冲突防覆盖。大表额外校验确认索引与全量有序遍历。

构建零警告、零错误。普通开发的构建/验证/必要重跑累计约 33 秒，单条均在 60 秒以内。中途一次精度夹具因新重复路径保护被拒绝，已改成两条独立路径，保留原子性断言后通过。

## 结果限制与下一步

private bytes 是测试后端进程某时刻的采样，包含运行时与 SQLite，未计入桌面 UI、音频播放 Host、GPU、插件，也不是峰值或长期稳定驻留值。分配量不能当作泄漏量。

本轮使用本机热缓存与短样本；32 次查询的分位数只作初步观察。真实大音频、HDD/NAS、系统压力、macOS/Linux 和持续播放并扫描尚未验收，不能外推这里的速度或内存。

完整旧库迁移、CUE/osu 虚拟曲目、封面、分析身份、专辑聚合、手动数据与后台播放降载按阶段补齐。每新增一项先明确 owner、队列/字节预算和兼容边界，再测实际增量成本。

原始 JSON 与日志在 Git 忽略的 misc/validation-20261002/，包括 smoke-run1/results.json、scale-run1/results.json 和 accuracy-run4/results.json；没有提交夹具、临时库或日志。

## 2026-10-19 扫描写入优化

本轮机器为 Windows x64、AMD Ryzen 9 7940H、.NET SDK 10.0.401，Release。使用真实文件、默认两个工作器、128 项批次、真实 SQLite/WAL 与 synchronous=FULL。对照为修改前保留的 v22 程序集；两边使用完全相同的 2048 文件夹具和扫描参数，各阶段重新建立独立曲库。文件位于本地，操作系统缓存已预热。

配对复测原始 CSV 为 `misc/scan-optimization-20261019/baseline-repeat.csv` 和 `optimized-final.csv`：

| 场景 | 修改前 | 修改后 | 吞吐倍数 |
| --- | ---: | ---: | ---: |
| 2048 WAV，同目录同专辑，首次扫描 | 9929 ms | 1535 ms | 6.47× |
| 同目录未变化复扫，开启缺失检测 | 188 ms | 67 ms | 2.81× |
| 同目录强制重读 | 4102 ms | 1159 ms | 3.54× |
| 128 个专辑目录、各 16 首 WAV/FLAC，首次扫描 | 2961 ms | 2415 ms | 1.23× |
| 混合目录未变化复扫，开启缺失检测 | 225 ms | 72 ms | 3.14× |
| 混合目录强制重读 | 2309 ms | 1773 ms | 1.30× |

首次原始基线的同目录首扫为 12254 ms；优化中途结果也有波动，表内采用保留旧程序后再次执行的配对结果。不能把单目录同专辑的倍数套到任意真实曲库。阶段时间是带并发重叠的观测值，不应相加当成总耗时。

同目录首扫全进程托管分配从约 313 MB 降至 50 MB（减少 84%）；强制扫描从约 554 MB 降至 48 MB（减少 91%）。混合目录复扫分配从约 16.9 MB 降至 8.4 MB（减少 50%）。这些数字是扫描期间累计分配，包含运行时与三个数据库 lane，并非驻留内存或泄漏量。两边强制扫描同时读取曲库页面；本轮最大响应分别约 21/20 ms（同目录）、5.3/6.6 ms（混合目录），只是短样本最大值。

### 实现与资源归属

- 主要瓶颈是逐曲重算专辑展示字段、逐曲读取专辑艺术家成员，以及未变化批次仍准备带完整触发器图的 metadata 写入语句。
- 专辑展示字段改为扫描批次内统一刷新；脏专辑 ID 保存在同一事务的 SQLite 表，提交前刷新并清空，失败/取消一起回滚。普通标签编辑等写入继续立即刷新。
- 艺术家成员查询增加覆盖索引，专辑成员遍历增加索引并按 128 项分页；一次批次只保留最多 256 条路径，避免把整张巨大合辑或整个艺术家表加载到托管内存。共享艺术家按最终专辑结果对齐，显式 album artist 保持自己的归属。
- 未变化批次不创建 metadata writer、艺术家 writer 或虚拟来源协调命令；来源 JSON 每条只序列化一次，在验证、回执指纹和入库之间共用。指纹通过 span 分段，保留原有回执计算语义。
- Core 继续是唯一 writer。扫描并发、队列容量、播放降载、文件变更复核、错误隔离、FULL 持久化和缺失检测条件保持原有约束；没有额外常驻任务、原生解码或整库缓存。

新增两个持久索引，2048 项夹具的数据库文件增加约 0.64–0.68 MiB；这是磁盘空间与查询速度的取舍。schema 23 增加扫描维护表/索引，schema 24 为早期 v23 触发器补上显式 UPSERT 冲突处理。v22 升级先生成 before-v23 一致性备份，已有 v23 使用 before-v24 备份；不会重复备份同一条升级路径。

## 2026-10-20 页面读取与扫描并行检查

本轮检查覆盖首页、歌曲、专辑、艺术家、流派与文件夹的数据库读取路径。Windows x64、.NET 10 Release、本地 SQLite/WAL；使用同样结构的新建夹具：6000 首生成曲目、300 个专辑目录、1200 条播放记录。每个接口先预热一次，再取 12 次样本；表内 P95 在这个小样本中等于最大值。数据只进入隔离测试库，未使用生产曲库。

| 读取场景 | 修改前中位数 | 修改后中位数 | 修改前/后 P95 |
| --- | ---: | ---: | ---: |
| 首页 | 28.689 ms | 14.553 ms | 99.784 / 25.130 ms |
| 文件夹第 2 页，200 行 | 4.977 ms | 2.336 ms | 11.116 / 7.776 ms |
| 歌曲首页，200 行 | 4.326 ms | 4.333 ms | 6.423 / 6.509 ms |
| 专辑首页 | 1.507 ms | 1.183 ms | 4.465 / 2.652 ms |
| 艺术家首页 | 0.378 ms | 0.493 ms | 1.065 / 1.430 ms |
| 流派首页 | 0.669 ms | 0.684 ms | 0.889 / 0.856 ms |

只有首页和文件夹路径有实现调整，其他接口作为对照观察，不能把其短测波动解释为优化收益。原始结果在 Git 忽略的 `misc/page-performance-20261020/baseline-run/results.csv` 与 `optimized-run/results.csv`，保留了修改前程序集。

首页过去在每次刷新时逐首通过托管函数提取目录并去重，还会为最近播放专辑重复聚合历史。现在曲库摘要按 library revision 复用单个四数字结果，最近播放聚合一次后连接专辑。播放时长、当天统计、最近播放和随机推荐仍查询当前事务，避免用整个首页缓存遮住播放进度变化。首页每次读取的全进程累计托管分配从约 3,928,380 bytes 降到 38,816 bytes，约减少 99%；这不是驻留或峰值内存。

文件夹统计按相同 revision 和实际筛选条件复用，翻页与改排序共用统计。缓存最多 16 个条目，只保存汇总数字及单目录查询键；每个路径最多 4096 字符，搜索最多 128 字符，不保留列表或封面。多目录查询、随时间变化的“最近”以及不通过 library revision 更新的封面/歌词资源条件继续即时计算。缓存由 Core 的 interactive reader 单线程持有，修订变化时失效，数据库释放后清空。没有增加索引、迁移、后台计时器或第二个业务 owner。

`PagePerformanceProbe` 的 19 项聚焦检查通过，覆盖首屏摘要、最近播放顺序、相邻分页、筛选隔离、播放进度即时变化、扫描后统计失效、旧 revision 拒绝、资源事实变更、多目录输入、缓存淘汰及取消。另在同一曲库中实际扫描 512 个 WAV，同时读取首页和文件夹；扫描约 513 ms，34 次读取的最大耗时约 22.1 ms，最终两个页面读取到的曲目数均为 6513。样本来自实际 ScanCoordinator、WAV metadata reader 和 SQLite writer，未包含音频设备播放。

聚焦检查可运行：`dotnet run --project tests/Echo.Library.Smoke -c Release -- page-performance <新的隔离目录>`。Core.Host Release 构建零警告、零错误。测试入口要求新目录，避免重复夹具混入统计。

上述时间只覆盖后端查询到结果返回，不包含 Core IPC、Avalonia 绑定/布局/呈现、封面解码及冷启动。真实大曲库、HDD/NAS、冷缓存、整棵进程树的稳定/峰值内存、后台 CPU、各页面完整首屏和快速滚动仍需独立测量；不能据此宣称所有页面性能已完成验收。
